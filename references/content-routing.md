# 内容路由与证据要求

本文件用于在生成封面前选择内容结构。六种结构是内容骨架，不是六套固定皮肤。每张封面只选一个主结构；确有必要时可以叠加一个辅助结构，但不得把多个结构的全部组件同时塞进画面。

## 总原则

1. 先判断内容承诺，再选版式。封面要让读者在缩略图尺寸下知道“讲什么”和“为什么值得点开”。
2. 先找证据，再写结论。标题中的版本、日期、参数、价格、排名、性能和“首次”“最强”等词都必须有可核验来源。
3. 事实、推断和个人观点分开表达：
   - **已验证事实**：可直接写进主标题或数据卡。
   - **基于证据的推断**：用“意味着”“可能”“我的判断”等限定语。
   - **个人体验**：用第一人称，不能伪装成普遍结论。
   - **待验证信息**：不得写成结论，可标“待测”或直接删除。
4. 真实截图、官方素材和用户照片承担“证据”作用；装饰背景不能冒充产品界面、测试结果或现场照片。
5. 如果证据不足，降低标题强度或切换结构，不为迁就版式编造内容。

## 快速路由

按顺序判断，命中最前面的明确条件即可：

1. 核心事件是否为新品、版本、开源、价格或能力更新？是 → **模型发布**。
2. 核心承诺是否为“跟着做就能完成一个操作”？是 → **工具教程**。
3. 核心问题是否为两个或多个对象在同一维度上的差异？是 → **模型对比**。
4. 核心价值是否为多个工具如何分工、衔接或自动化？是 → **工作流**。
5. 核心内容是否为解读一份官方公告、论文、文档或原始数据？是 → **官方证据**。
6. 核心内容是否来自作者亲历的活动、项目、测试或阶段复盘？是 → **现场复盘**。

如果同时命中多项，选择“读者点击后最先得到的价值”作为主结构。例如：“Qwen 新版发布后，我实测了三项能力”若正文以测试为主，应使用现场复盘或模型对比，而不是只因有发布事件就选模型发布。

## 六种结构

### 1. 模型发布

**适用条件**

- 新模型、新版本、开源、API 上线、价格调整、上下文窗口或模态能力更新。
- 正文重点是“这次发布了什么、和以前有什么不同、对谁有用”。

**推荐信息层级**

- 品牌或模型名。
- 一条明确变化，例如“开源”“支持图像与视频”“价格降至……”。
- 一至三个关键参数或能力标签。
- 官方模型卡、发布页或产品界面作为主证据。

**最低证据门槛**

- 至少一个官方发布页、官方文档、官方仓库、模型卡或论文链接。
- 核对准确版本、发布日期和关键参数；不同官方页面有冲突时注明口径。
- 使用官方 Logo 或模型图时记录来源和商标归属。

**不得做**

- 用传闻或搜索摘要宣布“已发布”。
- 把参数规模等同于能力强弱。
- 自制一张像官方页面的卡片却不标明“示意”。
- 无完整候选集合时写“最新”“第一”“最强”。

### 2. 工具教程

**适用条件**

- 安装、配置、接入、部署、迁移、排错或具体功能教学。
- 正文能给出可执行步骤，读者可复现结果。

**推荐信息层级**

- 动作型标题：工具名 + 要完成的结果。
- 难度、耗时、步骤数或适用对象中的一项。
- 一张真实界面、终端结果或前后对比。
- 必要时加入步骤编号或流程箭头，但不要把整篇教程缩进封面。

**最低证据门槛**

- 至少一次真实操作记录，优先使用用户截图、终端输出或可复现仓库。
- 明确软件版本、系统环境或验证日期；易变步骤需查当前官方文档。
- 封面展示的最终结果应与正文能交付的结果一致。

**不得做**

- 用无法执行的概念图假装真实产品界面。
- 在未跑通时写“零失败”“一键完成”。
- 截图中暴露密钥、邮箱、内部地址或个人信息。
- 通过极小的界面文字承担主要信息，导致手机端不可读。

### 3. 模型对比

**适用条件**

- 两个或多个模型、工具、方案或版本在相同任务上的比较。
- 正文重点是差异、取舍和选择建议，而非单个产品介绍。

**推荐信息层级**

- 对比对象名称和同一测试问题。
- 最多三至四个读者真正关心的比较维度。
- 一个有条件的结论，例如“写代码选 A，长文分析选 B”。
- 对比矩阵、同题结果或统一口径的数据图。

**最低证据门槛**

- 相同提示、数据集、环境、计费口径和时间窗口，或明确说明不可比项。
- 记录模型精确版本、测试日期、样本数和评分方法。
- 引用第三方榜单时保留榜单名称、版本和原始链接。

**不得做**

- 用品牌印象、图标大小或装饰色暗示未经测试的胜负。
- 混用不同版本、上下文长度、价格单位或不同时间的数据。
- 用单个样例推导“全面领先”。
- 没有结果时填入看似精确的分数；应显示“待测”或不展示该维度。

### 4. 工作流

**适用条件**

- 多模型、多 Agent、多工具之间的角色分工、数据流或自动化链路。
- 正文重点是“谁负责什么、如何衔接、何时需要人工确认”。

**推荐信息层级**

- 工作目标，而不是只罗列工具名。
- 三至五个角色或步骤，以及清晰的方向关系。
- 输入、关键交付物和人工检查点。
- 可选加入“我的分工”“推荐分工”标签，说明这是实践还是方案。

**最低证据门槛**

- 若声称为真实工作流，需有执行记录、项目文件、截图或日志佐证。
- 若尚未实际使用，必须标为“建议流程”“示意方案”或“待验证”。
- 涉及模型特长的分工，需要来自实测或官方能力说明。

**不得做**

- 把模型拟人化分工写成客观能力排名。
- 用箭头制造不存在的数据连通或自动化能力。
- 隐去人工审核、权限或隐私风险。
- 工具越多越显得专业；无关节点应删除。

### 5. 官方证据

**适用条件**

- 解读官方公告、更新日志、论文、政策、API 文档、模型卡或公开数据。
- 正文价值在于从原始资料中提炼影响，而不是简单搬运新闻。

**推荐信息层级**

- 官方事实或原文主题。
- 一句作者判断：“真正重要的不是 X，而是 Y”。
- 来源卡、关键段落高亮或原始数据图。
- 来源名称、发布日期和必要的版本信息。

**最低证据门槛**

- 必须读取原始页面或原始文件，不能只依据二手报道和搜索摘要。
- 核对发布日、更新时间、生效日和构建日分别指什么。
- 引用保持简短，准确保留上下文；其余内容用自己的话概括。

**不得做**

- 拼接或改写官方语句后仍加引号。
- 将作者推断包装成官方立场。
- 只截取有利段落，隐藏紧邻的限制条件。
- 生成伪造的公告、邮件或媒体报道截图。

### 6. 现场复盘

**适用条件**

- 活动现场、演讲、圆桌、项目经历、产品实测、阶段总结或增长复盘。
- 正文价值来自作者亲历、观察和复盘结论。

**推荐信息层级**

- 事件或任务名称。
- 一个具体结果、变化或反常识结论。
- 完整、有语境的真实照片；人物、动作和关键环境尽量保留。
- 最多三条可证实的收获、数据或方法。

**最低证据门槛**

- 照片需来自用户本人、明确授权素材或可合法使用的公开素材。
- 数字结果要有记录，个人感受要使用第一人称。
- 活动名称、日期、地点和作者身份必须真实，不暗示不存在的官方合作或背书。

**不得做**

- 为适配人物卡位切掉手、话筒、桌面等导致动作不完整。
- 美化或生成不存在的现场细节后仍称“现场照片”。
- 用个人一次经历概括所有用户。
- 让大照片吞掉标题空间；横版尤其要保护主标题和人物脸部安全区。

## 证据来源优先级

按任务相关性优先，其次遵循以下顺序：

1. 用户提供的原始材料、真实截图、项目文件和数据。
2. 官方公告、官方文档、官方 GitHub、模型卡、论文或公开数据集。
3. 可复现的一手测试与完整方法说明。
4. 高质量二手报道或社区讨论，仅作为线索或补充观点。

每次下载的 Logo、产品图、截图和照片都应记录：来源 URL、获取日期、用途、许可证或商标注意事项。找不到明确授权时，不把素材纳入可公开发布的成品。

## 失败与降级策略

- **没有官方来源**：不做发布确认或官方证据型封面；改为“传闻梳理”并明确不确定性，或暂停生成。
- **没有可比测试**：把模型对比改为“能力地图/待测计划”，所有结果标“待测”。
- **没有真实界面**：工具教程使用步骤示意并显著标“示意”，不要伪装成产品截图。
- **没有用户立场**：只总结经验证事实；不要代替用户制造个人观点。
- **人物素材不完整**：优先使用带环境的矩形照片卡，避免粗糙抠图和截断肢体。
- **标题事实超出证据**：缩窄标题范围，删除绝对化词语，直到每个核心词都能被证据支持。

## 输出前路由检查

- 一眼能否识别内容对象、核心动作和点击理由？
- 主结构是否只有一个，辅助结构是否真的必要？
- 标题中的每个数字、版本、排名和绝对词是否有来源？
- 证据画面是真实截图、明确示意，还是容易误导的仿真 UI？
- 个人观点是否用第一人称，建议流程是否标明为建议？
- 图片、Logo 与截图是否记录来源且具备使用条件？
- 在手机缩略图下，标题、主体和证据仍能被识别吗？

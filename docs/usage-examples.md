# 使用示例

下面的例子展示“用户最少需要提供什么”以及 Skill 应如何补齐。每个任务先生成一份 `COVER_PROMPT.md`，再把其中的精确文案、证据和构图写进 HTML 模板。示例里的事实在真正发布前仍需重新核实。

## 1. 模型发布

```text
$generate-xiaowei-covers
给 Qwen 最新正式发布的开源模型做公众号封面。
官方资料你自己查，不要把 preview 当正式发布。
主封面人物左下，方图做短标题。
```

预期行为：

- 检查官方发布总览、模型卡和仓库；
- 确认“最新”对应的发布日期语义；
- 选择 `model_release`；
- 写出包含六维视觉描述与三个画幅文案的 `COVER_PROMPT.md`；
- 生成 21:9、独立 1:1 和 pair preview；
- 把型号、参数、许可证与来源写入 `FACTS.md`。

## 2. 工具教程

```text
把这个 GitHub 仓库做成小红书教程封面：<repo-url>
重点是“从安装到第一次成功运行”，不要伪造终端结果。
```

预期行为：

- 选择 `tool_tutorial`；
- 证据区使用真实截图，或明确标注“界面结构示意”；
- 标题承诺的步骤必须在证据模块中出现；
- 人物左下，但不能挡住 UI 导航或关键操作。

## 3. 模型对比

```text
我想比较 Codex、Kimi、Grok 处理同一项研究任务的差异。
我还没有统一测试结果，先做一张不会误导人的候选封面。
```

预期行为：

- 不生成胜负榜或虚构分数；
- 优先降级为 `workflow`，或在 `model_comparison` 中标明待测；
- 只有统一输入、统一条件、统一指标后才填结果。

## 4. 多模型工作流

```text
公众号封面：Codex、Kimi、Grok 怎么分工？
我的实际分配是 Codex 调度执行、Kimi 读中文长文、Grok 补实时信息。
```

预期行为：

- 选择 `workflow`；
- 把内容写成“我的任务路由”，不是普遍排名；
- 使用三角色或三阶段证据模块。

## 5. 官方资料解读

```text
把这个官方 Release note 做成封面：<official-url>
不要只写“发布了”，要突出真正影响使用的三点。
```

预期行为：

- 选择 `official_evidence`；
- 证据区呈现来源、三个影响和作者判断边界；
- 不把自制卡片伪装成官方网页截图。

## 6. 活动复盘

```text
用这张现场照片做活动复盘封面。
主题是“一场分享后值得复盘的 3 件事”，保留手、话筒、桌面和水瓶。
```

预期行为：

- 选择 `field_recap`；
- 使用完整环境照片，不粗暴抠图；
- 个人经历和结论由用户提供或确认；
- 横版允许把现场照片扩大为主要证据。

## 7. 一次输出两个平台

```text
同一个选题做公众号和小红书两套。
公众号标题要更短，小红书可以多一行解释；不要互相裁切。
```

预期行为：

- 为 3:4、21:9、1:1 分别组织标题与内容；
- 共享主题和证据，不共享机械布局；
- 逐个画幅进行缩略图检查。

## 8. 只导出指定 route

```bash
node scripts/render-covers.mjs \
  ./cover.html \
  ./output \
  --only release
```

公众号模板会得到：

```text
wechat-01-release-21x9.png
wechat-01-release-1x1.png
wechat-01-release-pair-preview.png
```

竖版模板会得到：

```text
xiaowei-01-release-3x4.png
```
